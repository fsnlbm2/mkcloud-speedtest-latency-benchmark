## 测速之前，先弄清三个前提

**第一，官方宣传的延迟是“端内延迟”，不是你到网站的全程延迟。** 比如广港线路标注的 1~2ms，指的是广州入口到香港出口之间专线内部那一截，你本地到广州入口的公网段、以及香港出口到你目标网站的路程都不算在内。拿 1~2ms 去要求“ping 亚马逊后台也是 2ms”，属于用错尺子。

**第二，共享带宽是峰值，官方明确说不保证持续跑满。** mkcloud 的流量计费款按上行、下行双向统计，流量用完会停机，可以买流量重置或工单补差价升级。独享带宽款不限流量，但也不保证对任意目标 24 小时满速——本地宽带、对端服务器、协议开销都会影响结果。

**第三，测速数据直接关系到退款。** mkcloud 只支持质量问题退款，而且要求提交“准确具体的延迟数据、速度数据”作为证据，开通后也不支持换地域。所以下单当天就测，白天和晚高峰各测一轮，把结果存好，既是验货也是留证据。

## 第一步：用 ping 测延迟和丢包

开通后先在本地测入口 IP。Windows 用：


ping -n 100 入口IP


Linux/macOS 用：


ping -c 100 入口IP


对比平均值、最大值和丢包率。注意官方的两个提醒：出口 IP 不支持外部连入，不要拿本地直接 ping 出口当验收方法；ICMP 可能被限速或屏蔽，ping 不通不等于业务不可用，ping 正常也不代表 HTTPS 或远程桌面没问题。

测完本地到入口，登录 VPS 再测允许测试的目标，看 VPS 到你业务服务的延迟和丢包。两段分开看，才能定位问题出在入口接入还是出口之后的路由。

## 第二步：用 mtr 看路由路径

在 VPS 上对允许测试的目标跑 mtr 或 traceroute，白天和晚高峰各保存一份。路径数据主要用于定位问题，读的时候有两条官方提示值得记住：

- 中间节点显示丢包、但后续跳和终点不丢，先考虑是中间设备限制了探测包应答，别急着定性故障；
- 出现公网节点也不能证明跨境段是假专线，海外出口之后本来就可能有公网段；反过来跳数少也不等于物理独享。

mtr 的价值在于对比——同一目标、不同时段的路径变化，比单次截图有说服力得多。

## 第三步：用 iperf3 测真实吞吐

iperf3 需要你自己有（或获授权的）服务端，不能拿任意平台地址直接测。基本流程：


# 服务端
iperf3 -s

# 客户端测上传（8 并发，跑 30 秒）
iperf3 -c 服务端IP -P 8 -t 30

# 测下载
iperf3 -c 服务端IP -P 8 -t 30 -R

# UDP 模式测丢包和抖动（不限压测带宽）
iperf3 -c 服务端IP -u -b 0


几个容易踩的坑：

- iperf3 默认单线程，高带宽链路单连接可能跑不满，加 `-P` 并发或开多进程更接近真实上限；
- UDP 模式不加 `-b 0` 时有默认保护，只能压到 1Mbps 左右，结果会严重失真；
- 官网标注的 Mbps 要除以 8 才是下载工具里常见的 MB/s，200Mbps 对应约 25MB/s，别看到 25MB/s 就以为只有标称的八分之一；
- 从短时、低并发开始测，流量计费款双向计数，压测本身也烧流量。

参考值方面，RC Logs 那份广港 150Mbps 峰值套餐的实测，港内方向跑到了 135~140Mbps，接近打满；国际 speedtest（伦敦、纽约等远端）只有 50~120Mbps 不等。这个落差是正常的——专线优化的是端内和近距方向，跨大洋到具体目标的速度受对端和路由影响很大。所以验收时优先测端内和你实际业务方向，把 speedtest 当参考而不是判决书。

## 结果怎么解读：官方给的判断边界

| 指标 | 观察重点 | 不能直接推出 |
| --- | --- | --- |
| 延迟 | 相同源端、目标、时段的变化 | 单程时延、物理专线真假 |
| 路由 | 可见路径变化及终点响应 | 底层电路、带宽复用比 |
| 丢包 | 终点与实际业务是否同时异常 | 任一中间跳丢包就是故障 |
| 吞吐 | 两端能力、方向及套餐限制 | 一次跑满即可长期满速 |

两个高频疑问直接回答。晚高峰变慢是不是假专线？官方明确说不是，需要排查本地接入、服务器负载、跨境段、海外出口和目标限流，不能直接归因于商家切公网。测速和宣传对不上怎么办？先核对宣传的是端内还是全程，再提交同一目标、多个时段的结果给工单，这也是退款申请要走的流程。
